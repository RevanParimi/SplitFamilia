# The Android app: approach, settings and risks

SplitFamilia's Android app is a **Trusted Web Activity (TWA)**: a small Android app that opens the
live web app, https://splitfamilia.up.railway.app, full screen in the phone's browser engine
(Chrome, or another browser that supports TWAs). It was generated with
[Bubblewrap](https://github.com/GoogleChromeLabs/bubblewrap) and lives in [`android/`](../../android/).
Story SF-012 (task T-05), decided by D-0 on 2026-09-28.

How to build and sign it: [BUILD_RELEASE.md](BUILD_RELEASE.md).

## Why a TWA

- **One app, not two.** The web app stays the single source of truth. Every Railway web deploy
  updates the Android app on every phone at once. A new Play upload is needed only when the
  Android wrapper itself changes (its version, icon, colours or settings).
- **Invite links keep working.** A link like `https://splitfamilia.up.railway.app/?g=<code>`
  opens the app when it is installed (the verified link filter below) and the website when it
  isn't. The phone's groups, offline copy and waiting changes are the website's, as today.
- **Smallest change.** Nothing in the web app changes. Capacitor was considered and rejected
  (D-0): it bundles the files into the app, so the pages would run at `https://localhost`, every
  web change would need a Play upload, and invite links would need rework.

## What is in `android/`

| File | What it is |
|---|---|
| `twa-manifest.json` | Bubblewrap's settings for this app. Everything else in the project is generated from it |
| `app/build.gradle` | Generated by Bubblewrap; one line added at the end: `apply from: 'release.gradle'` |
| `app/release.gradle` | **Ours (SF-013):** release shrinking and upload-key signing. Not part of Bubblewrap's template |
| `app/src/main/AndroidManifest.xml`, `java/`, `res/` | Generated: the launcher activity, the icons, the splash screen, colours and strings. `res/xml/shortcuts.xml` is kept as the build's own `generateShorcutsFile` task rewrites it (without Bubblewrap's licence header), so a build leaves the working tree clean |
| `keystore.properties.example` | **Ours (SF-013):** the template for the git-ignored `keystore.properties` |
| `.gitattributes` | **Ours:** keeps `gradlew` with LF line endings, so it runs from a fresh clone on Windows too |
| `store_icon.png` | Generated by Bubblewrap: the 512 x 512 icon (the same image as `icon-512.png`) |
| `manifest-checksum.txt` | Bubblewrap's record of the `twa-manifest.json` it last generated from |
| `gradlew`, `gradlew.bat`, `gradle/` | The Gradle wrapper (Gradle 8.11.1, downloaded on first use) |

Never in git: the upload keystore, `keystore.properties`, passwords, `local.properties`, `build/`,
`.gradle/`, and any `.aab` or `.apk` (all in `.gitignore`).

### Permissions (checked in the merged release manifest, not the template)

The app asks for **no Android permission at all**. The browser does the networking, so a TWA
needs no `INTERNET` permission (Bubblewrap adds it only for the WebView fallback, which is off).
The merged manifest has one entry that looks like a permission:
`com.splitfamilia.app.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`. AndroidX adds it to every app:
it is the app's own signature-level permission, private to the app, and the user never sees it.
There is no `POST_NOTIFICATIONS`, no location, no Play Billing and no `AD_ID`. Cleartext (HTTP)
traffic is off: there is no network security config and no `usesCleartextTraffic="true"`, and
apps that target Android 9 or later default to off. Evidence: checks M1 to M6 and B3 of
`docs/planning/evidence/T-05-android-checks.mjs`, in the T-05 receipt.

### The launcher icon

`icon-512.png` (the owner's image, D-19) is a full square with the "S" inside the central 80%
circle, the safe zone a round mask keeps. Bubblewrap turned it into an adaptive icon (`ic_maskable`
on a white layer, inset 8.5 dp) and a full-square icon for Android 5 to 7. The circle-mask check
is `docs/planning/evidence/T-05-icon-mask-check.png`. No separate `icon-maskable-512.png` was
needed, so the web app's files and its service-worker cache are unchanged.

## How the project was generated (and how to regenerate it)

`bubblewrap init` asks its questions interactively. To get the same result from a script, T-05
built `twa-manifest.json` the way `init` does (Bubblewrap's own `TwaManifest.fromWebManifest`
on the live `manifest.json`), set the answers in the table above, and ran
`bubblewrap update --skipVersionUpgrade`, which generates the whole Android project from that
file.

To change a wrapper setting later (a colour, the version, the icon):

1. Edit `android/twa-manifest.json`.
2. In `android/`, run `npx @bubblewrap/cli@1.25.0 update --skipVersionUpgrade` (or without
   `--skipVersionUpgrade` to raise the version). Bubblewrap asks once for the JDK and Android SDK
   folders and saves them in `%USERPROFILE%\.bubblewrap\config.json`.
3. **Put back the one line Bubblewrap removes:** `apply from: 'release.gradle'` at the end of
   `android/app/build.gradle`. Without it the release build has no signing config (Gradle makes
   an unsigned bundle, which Play refuses) and doesn't shrink resources.
   `git diff android/app/build.gradle` shows the missing line. `npm test` fails until it is back.
4. Build and check as in [BUILD_RELEASE.md](BUILD_RELEASE.md). Bubblewrap also puts its licence
   header back into `res/xml/shortcuts.xml`; the first build removes it again. Keep the file as
   the build leaves it.

Use Gradle, not `bubblewrap build`, for release builds: `bubblewrap build` signs with its own
prompt-based flow and its own keystore path, not with `release.gradle`.

## Verified links: how the app hides the browser bar

Android shows the site full screen, without an address bar, only when two things match:

1. the app's link filter (`autoVerify`) for `splitfamilia.up.railway.app`, and
2. the site's `/.well-known/assetlinks.json`, which must list the SHA-256 fingerprint of **the
   key that signed the installed app**.

Today `assetlinks.json` holds two placeholders, `<UPLOAD_KEY_SHA256>` and
`<PLAY_APP_SIGNING_SHA256>`. Until they are replaced, the app opens the site in a Custom Tab with
an address bar: it works, but looks like a browser. Apps installed from Google Play are signed
by Google's **app signing keys**, so those fingerprints are the ones that matter for testers and
users; the upload key's fingerprint matters only for a build installed by hand. A new app is
enrolled in Play's "quantum-ready, hybrid signing", and Play then lists **three** keys whose
fingerprints must all be registered ([Play App Signing](https://support.google.com/googleplay/android-developer/answer/9842756),
checked 2026-10-01 IST), so `assetlinks.json` may end up with four entries. `npm test` accepts
two to five. Both steps are
in [BUILD_RELEASE.md](BUILD_RELEASE.md) (MANUAL ACTION REQUIRED). Changing `assetlinks.json` is a
web deploy, so it needs the owner's word.

## Risks

- **The phone needs a browser that supports TWAs.** Chrome does (it is on almost every Android
  phone), as do several other browsers. Without one, Android Browser Helper opens the site in a
  Custom Tab (with an address bar). The web app's data on the phone (its groups, offline copy and waiting changes) lives in that
  browser's storage for the site, not in the app.
- **Verification can fail.** With a wrong or missing fingerprint in `assetlinks.json`, or a
  host that serves it badly, the app still works but shows an address bar (above). The
  fingerprints are set after the owner's first upload (BUILD_RELEASE.md).
- **Google Play's "limited functionality" and "webview spam" policies.** Play does not allow
  "apps that only have limited functionality and content" or apps "that install, but don't
  load" ([Functionality, content and user experience](https://support.google.com/googleplay/android-developer/answer/9898783)),
  nor apps whose "primary purpose is to provide a webview of a website without permission from
  the website owner" ([Spam](https://support.google.com/googleplay/android-developer/answer/9899034));
  both checked 2026-10-01 IST. SplitFamilia is the owner's own site and a working app (groups,
  expenses, balances, settle-ups, offline use), so neither should apply, but Play's reviewers
  decide. The reviewer steps are in SF-016's `REVIEWER_ACCESS.md`. If the site is down, the app
  only shows the page's own offline copy (after a first visit), so Railway's uptime matters at
  review time.
- **The address is permanent.** `splitfamilia.up.railway.app` is built into the app and every
  invite link (D-10). Moving off Railway later means a new Android release and new invite
  links.
- **Large screens may rotate.** From Android 16, for apps that target API 36, Android ignores
  orientation locks on large screens (tablets, unfolded foldables). The page's layout is
  responsive, so it still works there.
- **Not yet seen on a real phone.** T-05 had no Android device or emulator. The build, the
  merged manifest and R8's output were checked, but the app was not launched; the page's in-app
  detection (`android-app://` referrer, SF-010) is still only simulated. The first real launch
  is the owner's internal-testing install (T-06, SF-018).
