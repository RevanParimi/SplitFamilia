# SF-004 — Split and settle in exact paise

Priority: **P0** · Task: **T-02** (story 3 of 5) · Estimate: **2 points**

Status lives in [STATE.json](../STATE.json), not in this card. Dependencies: SF-001.

Brief: [stage 1 (error handling) and stage 7 (expense splitting, balance
calculations)](../brief/2026-09-28-google-play-release-brief.md). Invariants:
[REVIEW.md](../REVIEW.md#this-apps-invariants).

## Intended result

Every expense splits into whole paise that add up exactly to its total. Every group's balances
add up to exactly zero, and following the suggested payments leaves everyone at exactly zero.
For example, ₹100 split three ways is ₹33.34 + ₹33.33 + ₹33.33, and every phone gives the extra
paisa to the same person.

## Starting points

- `money.js` (from SF-001).
- `index.html` `fmtAmount()` (lines 561–564) and the add-expense handler (lines 817–833, which
  uses `parseFloat`).
- Today, `computeBalances()` divides floats (`exp.amount / exp.split.length`), and
  `simplifyDebts()` hides the rounding error with a 0.005 threshold.

## Acceptance criteria

- Amounts become integer paise at read time: `Math.round(amount * 100)`. The stored format does
  not change. `amount` stays a decimal number in Firestore, so no data migration is needed.
- Each share is `floor(total / n)`. The leftover `r` paise go one each to the first `r` split
  members, **sorted by person ID**, so the result doesn't depend on the order of the split
  array.
- Balances are integer paise and sum to exactly 0 for any data. `simplifyDebts()` works in
  integers with no tolerance constants, and applying its payments leaves every balance at
  exactly 0.
- An expense that mentions a removed person (possible when two phones edit at once) no longer
  makes money vanish. That person's share stays in the balances and is shown as "Removed person".
  This deliberately changes the SF-001 characterisation. Record it as a decision.
- Amounts are shown with two decimals, from paise.
- The form rejects, with a clear message: an empty or non-numeric amount; zero or less; more
  than 2 decimals; more than a maximum held in one constant (proposal: 1,00,00,000.00, which the
  owner may change).

## Required tests

Expected values worked out by hand (paise):

- 10000 among [a, b, c] → a 3334, b 3333, c 3333. The same split given as [c, a, b] → the same
  result.
- 1 among [a, b, c] → a 1, b 0, c 0.
- A pays 10000 split A/B/C, and B pays 5000 split B/C → A +6666, B −833, C −5833, which sums to
  0 → settlements C→A 5833, B→A 833.
- A legacy float `0.30000000000000004` → 30 paise.
- Property check: for 1000 random groups and expenses, balances sum to 0 and the settlements zero
  every balance.
- Break check: put back float division, confirm the sum-to-zero test fails, then restore.

## Follow-ups from the SF-001 review (2026-09-29)

These were found in [the SF-001 review](../evidence/SF-001-review.md). They were already in the
code before SF-001, which had to keep behaviour unchanged. SF-004 fixes them, because it
rewrites the same functions.

- **F-1, a frozen page (medium).** Today a balance of ±Infinity makes `simplifyDebts()` loop
  forever, so every phone that opens the group freezes. Two ₹1e308 expenses entered through the
  form are enough, and so is a stored `amount: Infinity`. The form limit above stops new
  entries, but documents already stored need a read-time guard too:
  - an expense whose stored `amount` is not a finite number in (0, max], such as `1e308`,
    `Infinity`, `NaN` or `"300"`, stays out of the balances and is visibly flagged in the
    ledger, so someone can delete it;
  - `simplifyDebts()` always ends.
  - Tests: those four amounts, plus two ₹1e308 expenses, give finite balances that sum to 0,
    and the call returns.
- **F-2, built-in names (low).** `in` also matches `Object` built-ins, so a payer or split ID of
  `"constructor"`, `"toString"` or `"__proto__"` is not treated as missing. Use own-property
  checks (`Object.hasOwn`, or a `Map`). Test: an expense paid by the missing person
  `"constructor"` is handled exactly like one paid by any other missing person.
- **An empty or missing `split`** (from the SF-001 implementation receipt): today an empty split
  divides by zero (the share becomes Infinity) and credits the payer with nobody debited, and a
  missing `split` throws. Decide what happens, record the decision with an example, and test it.
  Flagging it like F-1 is the simplest option.

If these grow the story past one focused review, record a split in STATE.json first.
