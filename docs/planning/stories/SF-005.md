# SF-005 — Broken invite links show a message instead of breaking the app

Priority: **P0** · Task: **T-02** (story 4 of 5) · Estimate: **1 point**

Status lives in [STATE.json](../STATE.json), not in this card. Dependencies: SF-001.

Brief: [stage 1 (app startup failures, error
handling)](../brief/2026-09-28-google-play-release-brief.md).

## Intended result

Opening a mistyped or tampered invite link, for example `?g=goa/trip`, shows the join screen
with "That group link isn't valid." Today, `resolveGroupId()` saves the raw value and passes it
to Firestore. A `/` makes `doc()` throw, and because the bad value was saved to `localStorage`,
the app stays broken on every launch until storage is cleared.

## Starting points

- `index.html` `slugify()` and `resolveGroupId()` (lines 486–498), and `startApp()` (lines
  547–554, which builds the Firestore paths from the group ID).

## Acceptance criteria

- A group ID from the URL or from `localStorage` is used only if it matches the allowed pattern:
  lowercase letters, digits and single hyphens, no leading or trailing hyphen, at most 80
  characters. That covers every `slugify()` output and the codes from SF-006.
- An invalid value is never saved. An invalid value already in storage is cleared. The join
  screen shows a plain message.
- Valid existing links, such as `?g=goa-trip-2026`, open as before.
- The check is a pure function in a module, tested with `node --test`.
- Bump the service-worker cache name.

## Required tests

- Accepted: `goa-trip-2026`, `a`, `x1-y2`.
- Rejected: `goa/trip`, `""`, `-x`, `x-`, `a--b`, `GOA`, `..`, `__x__`, and an 81-character ID.
- Manual: open `http://localhost:8000/?g=goa/trip` → the message appears. Reload → the join
  screen still shows, and nothing is stored.

## Decision for the implementer

Uppercase `?g=` values are rejected, not lower-cased. Lower-casing would quietly open a
different Firestore document. Record this as a decision.

## Rollout and rollback

- Web deploy with a cache bump. Rolling back is a revert.
