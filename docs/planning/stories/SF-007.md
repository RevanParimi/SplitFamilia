## Intended result

The database stops being wide open. It accepts only ledger-shaped data for a group whose code you
already know, and nobody can list every group. The rules live in git and pass emulator tests
before the owner deploys them. For example, a script that asks for "all groups" is refused, and a
write of `{amount: "lots"}` is rejected.

**Owner input (D-6, 2026-09-28):** the owner has written no rules, and the Rules tab shows no
test-mode expiry date. So the database is probably fully open today, and there is no deadline
(PC-001 is done). These rules must be deployed before the Play release; the owner deploys them
when ready.

## Starting points

- There is no `firestore.rules` or `firebase.json` in the repo.
- The data paths (`index.html` lines 552–554) are `groups/{gid}`, `groups/{gid}/people/{pid}` and
  `groups/{gid}/expenses/{eid}`.
- The writes the app makes today (`index.html`):
  - people: `{name}` (line 776);
  - expenses: `{date, desc, amount, paidBy, split}` (lines 789–795);
  - the group document: `{currency}`, merged (line 814);
  - deletes of people and expenses (lines 785, 799).
- Tools: this machine has no Java or firebase-tools. The emulator needs a JDK, which needs **D-8**
  (the owner's OK to install). D-8 is approved, so install one.

## Acceptance criteria

- `firestore.rules`, and a `firebase.json` with only a `firestore` section, are committed.
  Hosting is on Railway, not Firebase (D-3).
- Minimal and safe. Default deny. Allowed:
  - `get` on `groups/{gid}`;
  - create or update of `groups/{gid}` with the key `currency` only (a string of 1–3
    characters);
  - `get` and `list` on `groups/{gid}/people` and `groups/{gid}/expenses`;
  - creating a person with `name` only (a string of 1–60 characters);
  - creating an expense with exactly `date` (string), `desc` (string of 1–200 characters),
    `amount` (a number > 0 and ≤ 10,000,000), `paidBy` (string) and `split` (a list of 1–50
    items);
  - deleting people and expenses.
- `gid` must match `^[a-z0-9]+(-[a-z0-9]+)*$` and be at most 80 characters. That is the same
  pattern SF-005 enforces in the app, and it covers every group made so far.
- Denied: listing `groups`, collection-group queries, updates to people or expenses (SF-022 and
  SF-023 will open exactly what they need), extra fields, and any other path.
- The UI's `maxlength` on name and description matches the rules. Bump the service-worker cache
  name.
- Emulator tests (`@firebase/rules-unit-testing`, with a `demo-` project ID so they can never
  reach the real project) cover every allow and every deny, and run with `npm run test:rules`.
  `npm test` stays network-free.
- **Deploying is the owner's action** (CLAUDE.md §5). The command is
  `npx firebase-tools deploy --only firestore:rules --project splitfamilia-cf927`. Add a
  `pending_check`: after the deploy, open an existing group on the live site → it loads, adding
  an expense works, and deleting it works.
- The receipt records what the owner saw in the Rules tab (PC-001), so a rollback target is
  known.

## Required tests

- Each allowed case passes and each denied case fails on the emulator. List them all in the
  receipt.
- Break check: loosen one rule (for example allow `list` on `groups`), confirm a test fails,
  then restore.

## Follow-ups from T-02 (2026-09-29)

T-02 added two kinds of Firestore access. The rules above already allow both; the emulator tests
must cover them:

- **Starting a new group** writes `groups/{gid}` with `{ currency: "₹" }` (a merge) at once, so
  the group exists before anyone is added.
- **"Join"** reads from the server: `get` on `groups/{gid}`, and `list` on
  `groups/{gid}/people` and `groups/{gid}/expenses` with `limit(1)`.

The app's limits live in one place each: `MAX_AMOUNT_PAISE` in `money.js` (₹1,00,00,000.00, so
`amount ≤ 10,000,000`) and the group-code pattern in `group-code.js`. Keep the rules equal to
them.
