# SF-008 — The app opens offline, and says so clearly when it can't start

Priority: **P0** · Task: **T-03** (story 2 of 5) · Estimate: **2 points**

Status lives in [STATE.json](../STATE.json), not in this card. Dependencies: SF-001.

Brief: [stage 1 (app startup failures, network failures, backend availability
failures)](../brief/2026-09-28-google-play-release-brief.md).

## Intended result

After one visit, opening the app with no signal shows the group's ledger from the phone's cache.
If the app truly can't start, for example on a first launch in airplane mode, it shows "Can't
reach Splitsheet. Check your connection." with a Retry button, instead of a join form that does
nothing.

Why: the service worker skips all cross-origin requests (`service-worker.js` line 30), so the
Firebase SDK from `www.gstatic.com` is never cached. Offline, the module import fails and none
of the script runs. Firestore's offline cache never gets a chance. The join screen is visible by
default in the HTML, so the user sees a form whose button just reloads the page.

## Starting points

- `service-worker.js` (the fetch handler, lines 25–45).
- `index.html`: the imports (lines 465–469), the join screen (lines 373–385) and the service
  worker registration (lines 888–892).

## Acceptance criteria

- The app shell and the exact, versioned Firebase SDK files (12.17.1: `firebase-app.js`,
  `firebase-firestore.js` and anything they import) are available offline. Two approaches are
  acceptable:
  - the service worker caches those gstatic URLs cache-first (they are immutable); or
  - the files are vendored into the repo.
  Record the choice. Firestore channels, fonts and every other cross-origin request still go
  straight to the network.
- If the SDK fails to load or initialise, a boot-failure panel shows a plain message and a Retry
  button. The join form never does a native form submit.
- With airplane mode on after one online visit, the ledger renders from Firestore's local cache.
- Bump the service-worker cache name.

## Required tests

- Manual in Chrome DevTools, recorded in the receipt:
  - visit online, go Offline, reload → the ledger shows;
  - clear site data, go Offline, load → the boot-failure panel shows, then Retry works once
    online;
  - block `www.gstatic.com` → the boot-failure panel shows.
- Any new pure helper gets a `node --test` case.

## Follow-ups from T-02 (2026-09-29)

The line numbers under "Starting points" predate T-02, which changed `index.html` and
`service-worker.js`. See [the T-02 receipt](../evidence/T-02-implementation.md).

- **Module versions.** The page now imports `./money.js?v=N` and `./group-code.js?v=N`, where N
  is the number in the cache name, and the worker never replaces a cached `?v=` URL. A test
  enforces the match. Keep this when adding the SDK files: an old worker must never hand a new
  page an old module (T-02 reproduced exactly that, a `SyntaxError`, before adding `?v=`).
- **One cache entry per invite link.** The worker caches every same-origin GET, so each
  `index.html?g=<code>` opened becomes its own cache entry (T-02's check saw 9 copies of
  `/index.html`). The group codes sit in the phone's cache keys and the cache grows. Consider
  answering navigations from the cached `./index.html`.
- **The browser's HTTP cache.** The worker now installs with `cache: "reload"`, but background
  refreshes and cache misses still go through the HTTP cache. Under a server without
  `Cache-Control` (for example `python -m http.server`), one open after an update still showed
  the previous page. SF-011's `no-cache` headers cover `index.html`; check the offline tests
  against them.

## Follow-up from the T-02 review (2026-09-29)
