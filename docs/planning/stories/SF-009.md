# SF-009 — Honest sync status and plain error messages

Priority: **P0** · Task: **T-03** (story 3 of 5) · Estimate: **2 points**

Status lives in [STATE.json](../STATE.json), not in this card. Dependencies: SF-008.

Brief: [stage 1 (error handling, network failures, loading states, logging, backend availability
failures)](../brief/2026-09-28-google-play-release-brief.md).

## Intended result

The group bar tells the truth: "connecting…", "live", "offline: changes will sync when you're
back online", or "2 changes waiting to sync". Errors are in plain words. For example, a
permission error says "This group can't be opened. Check the invite link." instead of Firestore's
raw message.

## Starting points

- `index.html`:
  - live sync and status (lines 837–860): "live" is shown even when data comes from the offline
    cache;
  - raw `err.message` in the status bar (lines 848, 854, 860);
  - `alert()` with `e.message` (lines 776, 785, 795, 799, 814).

## Acceptance criteria

- The status is driven by snapshot metadata (`fromCache`, `hasPendingWrites`, with
  `includeMetadataChanges`) plus the browser's online and offline events.
- Ledger rows not yet saved to the server are marked "waiting to sync".
- A pure function maps Firestore error codes to plain messages: `permission-denied`,
  `unavailable`, `resource-exhausted`, `failed-precondition`, `invalid-argument`, and a default.
  Users never see raw messages.
- Logging: at most `console.error` with the error code. User-entered text and group codes are
  never logged.
- A global `error` / `unhandledrejection` handler shows one friendly message instead of failing
  silently.
- Bump the service-worker cache name.

## Required tests

- `node --test`: each error code → its message, and an unknown code → the default.
- Manual:
  - DevTools Offline → the status says offline; add an expense → it appears marked "waiting to
    sync"; go online → the mark clears and the status says live;
  - with the rules emulator, or an invalid group, a permission error → the friendly message.

## Follow-up from the T-02 review (2026-09-29)

- **F-3 (medium): two groups can open in one page.** On the join screen, "Join" a code that
  exists, and while it says "Checking…" (up to 15 s on a slow network), start a new group. The
  new group opens; then the check returns and `openGroup()` runs again, so the page listens to
  both groups. The bar shows the joined group, but new people and expenses are saved to the new
  group, and either group's next update redraws the page with its own data. This story already
  touches the page's error and status flow, so fix it here:
  - open at most one group per page load (for example, return from `openGroup()` when a group is
    already open), and disable "Start group" while a check runs;
  - test: re-run part P3 of `evidence/T-02-review-probe.mjs`, which must show one group, with
    both writes going to it.
