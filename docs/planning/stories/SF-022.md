# SF-022 — Edit an expense

Priority: **P1** · Task: **T-04** (story 1 of 5) · Estimate: **2 points**

Status lives in [STATE.json](../STATE.json), not in this card. Dependencies: SF-004, SF-007.

## Intended result

Fixing a typo or a wrong amount no longer means deleting and re-adding the expense. For example,
tap "Dinner ₹1,200", change it to ₹1,250, and the balances update on every phone.

## Starting points

- `index.html` `renderLedger()` (lines 653–700) and the add-expense form (lines 419–444).
- `firestore.rules` (SF-007) currently denies updates to expenses.

## Acceptance criteria

- An expense's description, amount, payer and split can be edited, with the same validation as
  adding.
- The rules allow `update` with the same shape checks as `create`, plus emulator tests.
- The balances recompute, and the expense is never counted twice.
- Bump the service-worker cache name.
- Update `RELEASE_TESTING.md`, `STORE_LISTING.md` and `PLAY_CONSOLE_DECLARATIONS.md` if they
  already exist.

## Required tests

- An edit changes the balances by exactly the difference (worked by hand), and they still sum
  to 0.
- Rules: a valid update is allowed; an update adding extra fields is denied.

## Follow-ups from T-03 (2026-09-29)

- `firestore.rules` builds the expense check in one function, `validExpense(data)`; an update rule
  can reuse it: `allow update: if validGroupId(gid) && validExpense(request.resource.data);`.
- Add the update cases to `tests/rules/firestore-rules.test.js`, and remove the expense half of
  its "denied: editing a person or an expense" test.
- An edit made offline shows "waiting to sync" on its ledger row (SF-009), as an add does.
- Right after editing `firestore.rules`, `npm run test:rules` may stop with "Change detected,
  updating rules..." and leave the emulator on port 8080 (T-03 receipt L13; what to do is in
  `FIRESTORE_RULES.md` section 2).

## Follow-ups from the T-03 review (2026-09-30)

See [the T-03 review](../evidence/T-03-review.md). This story is the next to change the page's
writes, so fix these here:

- **F-5 (medium): a delete the server hasn't confirmed isn't counted, so the bar can say
  "live".**
  - Firestore raises the snapshot after a local delete with `hasPendingWrites` false (the
    document just leaves the list), so `countPending` misses it. With the phone online but the
    server unreachable, deleting an expense left the bar on "· live" for 20 s while the server
    still had it. Offline, the delete wasn't counted ("changes will sync…" instead of "1 change
    waiting to sync").
  - Count the page's own unconfirmed deletes (people and expenses). For example, keep a set that
    `deleteDoc` fills and its settled promise empties, or use `waitForPendingWrites(db)`.
  - Replace the test "a pending delete leaves no document behind but still counts as 1": the SDK
    never produces that snapshot.
  - Check: re-run [T-03-review-probe.mjs](../evidence/T-03-review-probe.mjs). Expect "offline: 2
    changes waiting to sync" after the offline delete and add (`E2_offline`), and no "live" in
    `E6_onlineButUnreachable` until the server has the delete. An edit made offline must show as
    waiting too.
- **F-7 (low, test gap): no rules test deletes under a bad code.** Removing the code check from
  `allow delete` still passes 15/15 (break check R9). When adding the update rule, make "denied:
  codes the app would never make" also try deleting a person and an expense, and updating an
  expense, under each bad code. Confirm R9 then fails.

## Changed by the move to Railway (2026-09-30)

The owner moved the database to Railway too, with no dependency on Firebase (T-08, T-09).

- An edit is a change to the expense through SF-033's API, checked by the shared limits
  module, and queued offline by SF-036's outbox. The notes above about `firestore.rules`, its
  tests and L13 no longer apply.
- **F-5** is fixed by design in SF-036: the outbox counts every waiting change, deletes
  included. **F-7** is covered by SF-033's tests of every operation under bad codes. Check that
  both still hold for edits:
  - an offline edit counts as a waiting change;
  - an edit with a bad code is refused.
