# SF-026 — Firebase App Check against scripted abuse (stretch)

Priority: **P2** · Task: **T-07** (story 4 of 5) · Estimate: **3 points**

Status lives in [STATE.json](../STATE.json), not in this card. Dependencies: SF-011. **Stretch:**
do it only if the owner promotes it.

## Intended result

Only the real app, on the real site, can talk to the database. A script that copies the public
Firebase config can't write junk or run up the bill.

## Starting points

- `index.html` lines 465–483 (Firebase initialisation).
- App Check for web uses reCAPTCHA Enterprise or reCAPTCHA v3. It needs a site key, which is
  public, and switching on enforcement in the Firebase console, which is **the owner's action**
  (CLAUDE.md §5).

## Acceptance criteria

- The App Check SDK is initialised before Firestore, with the site key in the web config.
- A debug-token path works for localhost testing. Debug tokens are never committed.
- Enforcement stays **off** until the owner has watched the App Check metrics and switched it on.
  Add a `pending_check` for that.
- The declarations and privacy policy are updated for reCAPTCHA, which is another Google service
  that collects data.

## Required tests

- Manual: requests carry App Check tokens (the metrics show verified requests); the localhost
  debug flow works.

## Rollout and rollback

- Web deploy, then the owner enables enforcement. To roll back, switch enforcement off first,
  then revert.
