# SF-033 — The ledger API, with the same checks as the Firestore rules

Priority: **P0** · Task: **T-08** (story 3 of 4) · Estimate: **3 points**

Status lives in [STATE.json](../STATE.json), not in this card. Dependencies: SF-032.

## Intended result

The page can open a group, add and remove people and expenses, and change the currency through
the server's API. The server accepts only ledger-shaped data for a group whose code you already
know, as SF-007's rules did. For example, asking for "all groups" is impossible because there is
no such endpoint, and an expense of `"lots"` rupees gets a 400 with the code `invalid-argument`.

## Starting points

- `firestore.rules` and `tests/rules/firestore-rules.test.js`: the cases to carry over.
- `money.js`, `group-code.js`, `sync-status.js` (`friendlyError`).
- The T-03 review's F-6 and F-7 ([T-03-review.md](../evidence/T-03-review.md)).

## Acceptance criteria

- **One set of limits, shared by the page and the server,** in a pure module (for example
  `ledger-rules.js`, served to the page with `?v=N`):
  - the group-code pattern, and at most 80 characters;
  - a currency of 1–3 characters and a name of 1–60;
  - a description of 1–200;
  - an amount of 1 to `MAX_AMOUNT_PAISE` paise;
  - a payer who is one of the group's people;
  - a split of 1–100 of the group's people (F-6: the page refuses more than that before
    sending). It was 50 until the owner set 100 on 2026-09-30, because a group trek can have
    100 people;
  - at most 100 people in a group (the owner, 2026-09-30). Adding the 101st gets 409
    `failed-precondition` with `field: "group-full"`. Sending someone already there again still
    succeeds;
  - an ID of 1–64 letters, digits, `_` or `-`.

  `tests/wiring.test.js` checks the page's `maxlength`s against this module.
- Endpoints, all JSON:
  - `GET` a group: its currency, people and expenses, plus a version number that goes up with
    each change. An unknown code gives 404 `not-found`, which is what "Join" needs;
  - `PUT` the currency, which also creates the group;
  - `POST` a person;
  - `DELETE` a person, refused with 409 `failed-precondition` while any expense uses them;
  - `POST` an expense;
  - `DELETE` an expense.

  There is no endpoint that lists groups.
- **The group code travels in a request header, not in the URL,** so Railway's HTTP logs never
  record it. The server logs at most a method, a status and an error code: never a code, a name
  or a description.
- Errors use the codes the page already maps: `invalid-argument`, `not-found`,
  `failed-precondition`, `resource-exhausted`, `unavailable`. The page's `friendlyError` gets
  its own text for a refused write (F-6).
- Guessing is slowed: more than 30 requests with unknown codes from one address in 10 minutes
  gives 429 `resource-exhausted`. Bodies over 16 KB are refused, and so are requests that
  aren't JSON. The largest allowed expense (100 people with 64-character IDs) is about 8 KB.
- `POST` with an ID that already exists returns success without a second copy, so a replay is
  harmless.

## Required tests

- Every case from `tests/rules/firestore-rules.test.js`, as API tests on the in-process server
  with a temporary database. The expected statuses are worked out by hand.
- **F-7:** every operation (`GET`, `PUT`, `POST`, `DELETE`) with each bad code (`Goa-Trip`,
  `goa--trip`, `-goa`, `goa-`, `goa_trip`, 81 characters) is refused. Break check: skip the code
  check on `DELETE`, and a test must fail.
- A split of 101 is refused; a split of 100 is accepted, and so is the largest allowed expense
  (100 people with 64-character IDs) in one request.
- The 101st person in a group is refused; after someone is deleted there is room again.
- A person used in an expense can't be deleted.
- A duplicate `POST` leaves one row.
- The 31st unknown code gives 429.
- No log line contains the code or the typed text.

## Changes requested by the T-08 review (2026-09-30)

See [the T-08 review](../evidence/T-08-review.md). T-08 is `changes_requested` for F-8. Don't
push T-08 until the rework is accepted.

The owner took D-17's option (a) on 2026-09-30. The rework (same day) does F-8, F-9 with those
numbers, and N-4. See the "Rework" section of
[the implementation receipt](../evidence/T-08-implementation.md).

- **F-8 (high, must fix): the guess limit can be bypassed.**
  - The cause: `server/api.js` checks `limiter.blocked(address)` before it waits for a
    `PUT`'s or `POST`'s body, and counts the unknown code only after the wait.
  - The effect: requests whose bodies arrive after their heads all pass the check. 60 held
    requests with unknown codes all got 404, and 60 held `PUT`s created 60 groups. Expected:
    at most 30, then 429.
  - The fix: check `limiter.blocked(address)` again right after the body is read, before
    `ledger.groupVersion(code)`. From there on nothing waits.
  - Required test: 60 requests with unknown codes, each head sent first and each body after
    all the heads, as in `evidence/T-08-review-probe.mjs` (`P1_heldBodies`). At most 30
    answers other than 429.
  - Break check: remove the new check, and that test must fail.
- **F-9 (medium, the owner's numbers, D-17): no per-address limits on writes or streams.**
  - Anyone can make a group and then, from one address:
    - add 2000 of the largest expenses in about 9 s (28 MB, nothing refused);
    - hold every live stream, so a family's stream gets 503.
  - Recommended, in this rework if the owner agrees (D-17):
    - at most 300 changes per address per 10 minutes (then 429 `resource-exhausted`);
    - at most 10 open streams per address (then 503 `unavailable`, as when the server is
      full);
    - at most 5,000 expenses per group, deleted ones included (then 409
      `failed-precondition`, `field: "group-full"`).
  - A change that's already there (a replay) must still succeed in a full group, as it does
    for people. A 429 is fine, because SF-036's outbox tries again later. SF-037's import has
    its own endpoint, so these limits don't apply to it.
- **N-4 (note, optional):** `isDate` in `ledger-rules.js` takes impossible dates such as
  `2026-02-30T00:00:00.000Z` (V8 rolls it over to 2 March). A fix: also require
  `new Date(value).toISOString()` to give back the same date and time. The page never sends
  one.
