# SF-035 — The page uses the Railway API instead of Firebase

Priority: **P0** · Task: **T-09** (story 1 of 4) · Estimate: **3 points**

Status lives in [STATE.json](../STATE.json), not in this card. Dependencies: SF-033, SF-034.

## Intended result

The app looks and works as it does today: start a group, join with a link or code, add and remove
people and expenses, change the currency, and watch others' changes arrive live. But it talks
only to its own server on Railway. For example, a new expense is sent to the server's API, and
no request goes to any Google or Firebase address.

## Starting points

- `index.html`: the Firebase imports and `firebaseConfig`, `groupExists()`, `startApp()` (the
  three `onSnapshot` listeners and the mutations) and `updateStatus()`.
- `service-worker.js` (the `SDK` list) and `sync-status.js`.

## Acceptance criteria

- The page imports no Firebase SDK and holds no Firebase config. Its data calls go only to its
  own origin's API, through a small module (for example `ledger-client.js`, with `?v=N`).
- "Join" asks the API. A 404 shows "No group found with that code…" as today. Offline, it shows
  today's offline message.
- "Start a new group" creates the group with its currency straight away, as today.
- Live updates (SF-034) keep the ledger current. After a reconnect, the page fetches the whole
  group once, so a missed update can't leave it stale.
- Every error the user sees comes from `friendlyError`, never the server's text. F-6: a refused
  write gets its own text, not "Check the invite link".
- The worker drops its `SDK` list, never caches `/api/…`, and still starts the app offline
  (SF-036). The cache name and `?v=` are bumped.
- The start-up panel still covers a page that can't start.
- One group per page load (T-02's F-3) still holds.
- Every name and description still reaches the screen through `textContent`.
- `tests/wiring.test.js`: no shipped file mentions `firebase`, `firestore` or `gstatic`.

## Required tests

- `node --test` for the client module against the in-process server:
  - start, join (found, not found), add, remove and currency;
  - the error codes mapped to plain words.
- The browser check, with the T-03 probe's scenarios moved to the new server (`E1`–`E5`):
  - ₹100.00 and ₹0.05 split three ways give the hand-worked balances;
  - "live" when connected;
  - no request to a Google host except the fonts (until SF-025).

## Rollout and rollback

- It ships only at the cutover (SF-038), after the data is copied (SF-037). Deploying it earlier
  would show empty groups. Rolling back means redeploying T-08 and making Firestore writable
  again (SF-038's steps, in reverse).

## From T-08's implementation (2026-09-30)

T-08 left the page unchanged (see decision D2 in `evidence/T-08-implementation.md`), so these
page-side items move here:

- **F-6, the page's half:** refuse a split of more than `MAX_SPLIT` (100, the owner's number
  since 2026-09-30) before sending, with `checkExpense()` from `ledger-rules.js`. The server
  already refuses 101.
- **At most 100 people in a group** (`MAX_PEOPLE`, the owner, 2026-09-30): the form says so
  before sending the 101st, for example "This group already has 100 people." The server
  answers 409 `failed-precondition` with `field: "group-full"`.
- **At most 5,000 expenses in a group,** deleted ones included (`MAX_EXPENSES`, the owner,
  D-17). A family won't reach it. A 409 `group-full` on an expense gets its own text, for
  example "This group has reached its limit of 5,000 expenses." A 429 on a change (more than
  300 changes from one address in 10 minutes) is "try again later", as SF-036 says.
- **Plain words for the server's refusals:**
  - `invalid-argument` (400) already has its own text in `friendlyError`.
  - `failed-precondition` (409) now means "that person is in an expense" (`field: "in-use"`;
    another phone added one) or "the group is full" (`field: "group-full"`), not "the app is
    out of date". Give each its own text.
  - A 400's `field` (for example `"split"`) may pick the wording, but the server's own text is
    never shown.
- **What the page will call** (`server/api.js` lists it):
  - every request sends the `X-Group-Code` header;
  - amounts go as `amountPaise` (integer paise);
  - an add answers 201 (new) or 200 (already there), and every change answers `{ version }`.
- **Live updates:** use `watchGroup()` from `ledger-client.js` with `onVersion` (then fetch the
  group once) and `onState` (for the bar). Call `reconnectNow()` on the browser's `online` event.
- **New page modules:** load `ledger-rules.js` and `ledger-client.js` with `?v=N`. Add them to
  the worker's `SHELL`, the `Dockerfile`, `.dockerignore` and `server/static.js`
  (`npm test` fails until all agree).
- **To consider:** an invite link's `?g=<code>` still reaches the server in the page's own URL:
  on a first open, and when the worker fetches the page from the network. Railway's request log
  may record it. Two options:
  - the worker fetches `./index.html` without the query;
  - links carry `#g=`, which browsers never send, while `?g=` links keep working.

  **OWNER CONFIRMATION REQUIRED** before changing the link format.
