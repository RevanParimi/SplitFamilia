# SF-036 — Offline: the phone's copy and changes waiting to sync

Priority: **P0** · Task: **T-09** (story 2 of 4) · Estimate: **2 points**

Status lives in [STATE.json](../STATE.json), not in this card. Dependencies: SF-035. Owner
decisions: **D-14**.

## Intended result

What works offline today keeps working without Firebase. After one visit, the app opens with no
signal and shows the group from the phone's copy. Expenses and people added or removed offline
wait on the phone and are sent when the signal comes back. The bar counts every change still
waiting, deletes included. For example, delete "Tea" and add "Taxi" offline, and the bar says
"offline: 2 changes waiting to sync"; back online, both reach the server and it says "live".

(If D-14 chooses view-only offline, only the first part applies: the group is shown offline,
and changes need a connection. That is 1 point.)

## Starting points

## Acceptance criteria

- **The phone's copy.** The last group shown is kept in IndexedDB, with the code as its key
  inside the phone's storage, never in a URL. An offline open shows it at once, and the bar
  says "offline: …".
- **The outbox.**
  - Each change made on the phone gets its ID on the phone (`crypto.randomUUID()`) and is kept
    in an IndexedDB outbox.
  - The outbox is sent in order when the server can be reached. A change is removed only when
    the server confirms it.
  - Sending twice is harmless (SF-032: duplicate IDs are ignored).
  - A change the server refuses (400 or 409) is removed, with one plain message saying which
    change failed. It is never retried forever.
- **The honest status.** "live" only when the live connection is up and the outbox is empty.
  Otherwise "N changes waiting to sync", or "offline: …", or "connecting…". Deletes are counted
  (F-5). Rows not yet on the server say "waiting to sync".
- **Balances while waiting.** They include the phone's waiting changes, as today.
- **Two phones at once.** Adds from both are kept. A delete of something already deleted is
  harmless.

## Required tests

- `node --test` for the outbox as a pure module (a fake store and a fake network):
  - ordered replay;
  - one confirmed change removed, and a refused one dropped with its message;
  - a duplicate send leaves one row;
  - the count includes deletes.
- The browser check:
  - the T-03 probe's `E2`/`E3`: offline, delete then add; expect "offline: 2 changes waiting
    to sync"; online → "live", and the server holds exactly the expected rows;
  - `E6` (online, server unreachable): never "live" while a change waits;
  - an offline reopen shows the group.

## From T-08's implementation (2026-09-30)

How the server treats a change sent again (tested in `tests/server-api.test.js`):
- An add with an ID the group already has answers 200 with the current version, even if that row
  was deleted since: a delete only marks the row, so a late replay never brings it back.
- An expense sent again after its payer was removed still answers 200, because the first send
  got through.
- A delete of something already deleted, or never there, answers 200.
- So the outbox can treat any 2xx as "confirmed", and 400 or 409 as "refused: drop it and
  say which change failed".
- A 404 means the group itself is unknown.
- 429, 503 and network errors mean "try again later".

## From T-09's implementation (2026-09-30)

See [the T-09 implementation receipt](../evidence/T-09-implementation.md).

- `outbox.add()` only keeps a change; the page then flushes it. A change that must wait is
  tried again after 5 s, doubling up to a minute, or after the server's `Retry-After`. Where the
  browser has `navigator.locks`, two tabs never send at once.
- Only a 4xx other than 408 and 429 drops a change. A 500 or 503 waits and is tried again: a
  change is never dropped because the server had a bad moment.
- A change the server confirms moves into the phone's copy at once, so a row never blinks out
  between "waiting" and the next read.
- The old page's Firestore cache stays in the browser's storage on phones that used it. It is
  harmless, and it goes when the site's data is cleared (a limitation in the receipt).
