# SF-037 — Copy the groups from Firebase to the Railway database

Priority: **P0** · Task: **T-09** (story 3 of 4) · Estimate: **2 points**

Status lives in [STATE.json](../STATE.json), not in this card. Dependencies: SF-033. Owner
decisions: **D-16**.

## Intended result

Every group the family uses is copied from Firestore into the Railway database, with the same
people, expenses and IDs. Every balance then comes out the same to the paisa. For example, if
the family group shows "Chitra owes Asha ₹58.34" before the move, it shows exactly that after.

## Starting points

- The Firestore data (owner's screenshot, 2026-09-30): three groups under `groups/`. One has no
  group document of its own, only a `people` collection. The codes are not written in the repo.
- Firestore's REST API can read the data while its rules allow reads (the live rules allow
  everything under `groups/`; the stopgap rules, D-15, still allow reads by code).
- `money.js`: `toPaise`, `expenseProblem` and `computeBalances`.

## Acceptance criteria

- A script (for example `scripts/move-from-firestore.mjs`, not shipped in the image) takes the
  group codes as arguments, so they're never written in the repo. It reads each group with its
  people and expenses from Firestore's REST API, including groups that have no group document.
- **A dry run first**, with no writes. For each group it prints:
  - the counts of people and expenses;
  - each person's balance and the suggested payments, from `money.js`;
  - any expense `expenseProblem` flags. Those are listed for the owner to decide; they are not
    silently dropped;
  - any group over the owner's limits since 2026-09-30 (more than 100 people, an expense split
    among more than 100, or more than 5,000 expenses including deleted ones, D-17), for the
    owner to decide. The family's groups are expected to be far below them. (The 5,000 was
    added by the second T-08 review, N-7. If D-18 adds a cap on a group's split entries, list
    that too.)
- **The import** sends the data to the server over HTTPS, to an import endpoint that exists
  only while the Railway variable `IMPORT_TOKEN` is set (**MANUAL ACTION REQUIRED**: the owner
  sets it for the move, and removes it afterwards).
  - The token is never committed, printed or logged.
  - IDs are kept as they are, and amounts are converted to paise with `toPaise`.
  - Running it again adds nothing new (duplicate IDs are ignored).
- **After the import,** the script reads each group back from the API and compares the balances
  with the dry run. It passes only if every balance matches to the paisa.
- Running it against production needs the owner's word (CLAUDE.md §5: migrating data).

## Required tests

- `node --test` with fake Firestore responses:
  - a group with and without a group document;
  - an amount of `99.5` → 9950 paise;
  - a flagged amount (`"12"`) → listed, not imported, unless the owner says so;
  - a removed person still in a split: kept as that ID, so the balance matches.
- The balance comparison fails if one paisa differs (break check).
- An end-to-end run against a local server with a temporary database.

## Rollout and rollback

- Run at the cutover (SF-038). The Firestore data is left in place, read-only, as the fallback
  for the owner's safety period.
