# SF-038 — The switch-over, and removing Firebase

Priority: **P0** · Task: **T-09** (story 4 of 4) · Estimate: **2 points**

Status lives in [STATE.json](../STATE.json), not in this card. Dependencies: SF-035, SF-036,
SF-037. Owner decisions: **D-16**, **D-18** (from the second T-08 review).

## Intended result

The family moves to the Railway app and database in one short, planned step, and nothing is
lost or entered twice. Afterwards the repo, the app and the Android app have no dependency on
Firebase. Once the owner confirms, the Firebase project is deleted. For example, a phone still
on the old GitHub Pages address shows "SplitFamilia has moved" with a button that opens the same
group on the new address.

## Starting points

- `docs/google-play/HOSTING_RAILWAY.md` (section 6: moving phones off GitHub Pages) and
  `FIRESTORE_RULES.md`.
- Everything that mentions Firebase: `firestore.rules`, `firebase.json`, `tests/rules/`,
  `package.json`'s devDependencies, the docs, `CLAUDE.md`, `README.md` and `REVIEW.md`.

## Acceptance criteria

- **A switch-over guide** (for example `docs/google-play/MOVE_FROM_FIREBASE.md`) gives the
  order below. Every owner step is labelled **MANUAL ACTION REQUIRED**.
  1. The owner makes Firestore read-only by publishing the rules text the guide gives (`allow
     read` only). Old pages can still show the data, but can't write to the old database.
  2. The session runs SF-037's dry run and then the import, on the owner's word, and records
     the balance check.
  3. The owner's word to push T-09. Railway then serves the new page.
  4. The owner opens each group's invite link on the Railway address, on each phone, and
     reinstalls from there.
  5. After a safety period (D-16), the owner turns off GitHub Pages and deletes the Firebase
     project. The guide says where in each console.
- **The old address:**
  - when the page runs anywhere but its own server (GitHub Pages), it shows "SplitFamilia has
    moved" with a link to the same group on the Railway address, keeping the invite code;
  - `localhost` still works for development.
- **Removed from the repo:**
  - `firestore.rules`, `firebase.json`, `tests/rules/` and the three Firebase devDependencies,
    with `package-lock.json` regenerated;
  - the `test:rules` script, and `FIRESTORE_RULES.md`, replaced by the move guide.

  `CLAUDE.md`, `README.md` and `REVIEW.md` then describe the Railway server and database.
- **Checked by `npm test`:** no file in the image mentions Firebase, Firestore or gstatic.
- **Pending checks,** each written against what the code does:
  - after the push, each family group on the Railway address shows the same balances as the
    dry run;
  - a test expense is added and deleted;
  - the old address shows the notice.

## Required tests

- `node --test`:
  - the "moved" check on a GitHub Pages origin, the Railway origin and `localhost`;
  - the wiring test that nothing shipped mentions Firebase.
- A break check: put a `gstatic` URL back in `index.html`, and a test must fail.

## Rollout and rollback

- Until step 5, rolling back is:
  - redeploy T-08 on Railway;
  - publish the old Firestore rules again;
  - revert the push.

  Changes made on Railway after the switch would then need copying back by hand, which is why
  the safety period is short and watched. After step 5 there is no way back to Firebase, by
  design.

## Follow-up from the T-08 review (2026-09-30)

See [the T-08 review](../evidence/T-08-review.md).

- **N-5: `/healthz` must fail when the database does.** In T-08 it always answers 200 and only
  reports `"database":"unavailable"` (T-08's D14), because the page doesn't need the database
  yet. From the switch-over, a deploy that can't open the database would still pass Railway's
  health check and replace the working one. With this story, `/healthz` answers 503 when the
  database is unavailable, so Railway keeps the last good deploy. Add a test, and update
  `HOSTING_RAILWAY.md` section 3a.

## Follow-up from the second T-08 review (2026-09-30)

See the "Second review: the rework" section of [the T-08 review](../evidence/T-08-review.md).
T-08 was accepted. These must be settled before this story's switch-over.

- **F-10 (medium), D-18 (open, the owner's numbers): one read of a very large group is too
  costly.**
  - Anyone can make a group of their own and fill it to D-17's caps: 100 people with
    64-character IDs, and 5,000 expenses each split among all 100.
  - One read of that group (`GET /api/group`) is then 37.3 MB, built in 1.74 s while the server
    does nothing else. The answer is never gzipped.
  - With ten such reads in flight, the page's own `/` waited 16.7 s, and memory grew by about
    600 MB. Reads of a known code have no limit.
  - From the switch-over, that would stop the family's page, sync and live updates.
  - Recommended, D-18 (a), before the switch-over:
    - cap a group's split entries at 20,000 in all, deleted ones included. Then the largest
      read is about 5 MB. The cap goes in `ledger-rules.js`, and the page shows its own text
      for it, as for `group-full`;
    - gzip the API's answers when the browser asks;
    - build one answer per group version, shared by every reader.

    Then re-run the T-08 second review's probe (`evidence/T-08-review2-probe.mjs`, row Q8) and
    record the new size and time.
  - D-18 (b): accept the risk and watch Railway's metrics.
- **N-6 (note): the change limit sets a rate, not a total.**
  - One address at 300 changes per 10 minutes can add about 590 MB a day of the largest
    expenses. That fills a 50 GB volume in about 85 days, or about 9 days from ten addresses.
  - At the next edit of `server/api.js`, its opening comment should say the limits stop anyone
    filling the database *quickly*.
  - `HOSTING_RAILWAY.md` gains a step, **MANUAL ACTION REQUIRED**: check the volume's usage
    once a month. Railway's docs (2026-09-30) don't mention usage alerts: **VERIFY IN
    RAILWAY**.
  - Railway serves this host over IPv4 only today (no AAAA record). If it ever serves IPv6,
    the per-address limits must count an IPv6 address by its /64, or one client could use many
    addresses.
